## 1. 스크립토가 무엇인가 (버전0 최종 정의)

워드프레스 블로그의 **애드센스 승인 → 수익화 전 과정을 자동으로 밟아주는 도구**.
- 매일 아침 7시: 주제 선정(저경쟁 롱테일) → 글 생성 → 품질 게이트 → 예약 발행 → 색인 통지 → 사이트 점검·자동 수리 → 텔레그램 브리핑 (GitHub Actions, 서버비 0원)
- 아이폰 PWA 대시보드: 승인 여정 7단계 스테퍼, 원클릭 사이트 정리, 색인 신호등, 결산·글 비율 자동 조절
- 핵심 재정의(8/23): 경쟁 툴이 "하루 몇 편"으로 경쟁할 때, 스크립토는 **"몇 회차에 승인되는가"**로 경쟁한다.

## 2. 연대기 — 5막 구성 (강의 목차 그대로 사용 가능)

### 1막 · 순진한 대량생산 (7/3~8/18)
- 하루 26~30편, 47일간 1,235편 생성. "많이 쓰면 되겠지."
- 결과: 애드센스 반려 반복. 구글의 scaled content abuse 정책(검수 없는 대량 발행 금지)을 정면으로 걷고 있었음.
- **교훈 ①**: 병목은 생산이 아니라 '통과'다. AI 금지가 아니라 '검수 없음' 금지 — 검수를 자동화하면 정책을 지키며 자동화할 수 있다.

### 2막 · 원인 규명 (8/22~24)
- 라이브 사이트 전수 분석: 제목 어미 중복 50%, 상투 도입부 100%("~인 줄 알았습니다"), 글 1개짜리 태그 아카이브 1,976개, 니치 불일치(메뉴는 인테리어, 글은 지원금).
- **충격 반전**: 생성 프롬프트 자체가 "총정리로 제목 지어라, 직접 해본 것처럼 써라"라고 지시 — **반려 원인의 절반은 내 코드였다.**
- 대응: 품질 게이트(기계 검사)와 생성 프롬프트를 한 몸으로 재설계. 니치 확정(셀프 인테리어), 태그 전량 삭제, 지원금 글 비공개.
- **교훈 ②**: 탐지기를 만들면 반드시 생성기와 대조하라. 자기 손으로 만든 함정에 자기가 빠진다.

### 3막 · 앱이 프로그램이 되다 (8/23~30, v32→v121)
- UI 전면 개편: 설명문 4,275자→169자, 설정 입력칸 34→8, 하단 탭바(글/승인/수익/설정), 승인 탭 = 실행 주체.
- 사고와 방어의 반복(전부 실화, 강의 소재):
  - 제목 재작성 파서가 줄 순서로 짝을 맞춰 **엉뚱한 글에 남의 제목이 붙음**(6편) → 워드프레스 리비전으로 복구, 번호 기반+유사도 검증으로 재발 방지
  - 빈 화면 값이 설정을 덮어 앱 비밀번호 소실 → touched 기반 저장
  - iOS에서 overflow-x:hidden이 하단 탭바를 띄움 → clip으로 해결
- 니치 오염 사고: 옛 카테고리 시크릿이 지원금 초안을 계속 생성 → **설정 단일 소스**(저장소 파일 > 시크릿) 원칙 확립.
- **교훈 ③**: 자동화의 절반은 '방어'다. 실패는 관측 가능해야 하고(화면 배너·로그), 같은 실수는 구조로 막는다.

### 4막 · 색인의 재발명 (8/31)
- 중대 발견: **글 29편 전부 "URL is unknown to Google"** — 5회 반려의 숨은 원인은 콘텐츠 이전에 '구글에겐 빈 사이트'였다는 것.
- 색인 요청 버튼엔 API가 없다 → 목적을 분해: ①재크롤 유발 ②확인. URL Inspection API(하루 2천 회)가 ②를 완전히, ①을 부분 대체. 여기에 IndexNow(네이버·빙)+WebSub(구글 RSS 푸시)+사이트맵 자동 제출을 얹어 "발행하면 알아서 알림"을 완성.
- 가짜 1인칭 경험담 22편 적발·전량 교정(정책 위험 + 자기 탐지기에 걸리는 자충수) — "자격이 아니라 방법만 말한다" 원칙.
- **교훈 ④**: "그 버튼엔 API가 없어요"에서 멈추지 말 것. 버튼의 '목적'을 분해하면 대체 경로가 보인다.

### 5막 · 자동 운영과 진실의 아침 (8/31~9/1, v122→v130)
- 점검·수리의 서버 이전: 매일 채점→미달 글 자동 재작성(캡 5편)→텔레그램 브리핑. 실측 31편 평균 96점.
- 9/1 하루에 잡은 오류 7종(전부 실측 재현→수정→프로덕션 검증):
  ①GitHub 크론 스킵(백업 크론+중복 가드) ②images.py에 모듈이 통째로 2번 들어가 수정본을 옛 코드가 덮던 사고 ③품질 게이트 폐기 시 그날 발행 0편(보강 재작성 1회 구제) ④삭제 글의 구글 검색 잔재(고스트 자동 감지) ⑤결과 push 조용한 유실의 진짜 원인(rebase가 unstaged 변경에 거부 → autostash) ⑥낡은 CI 픽스처 ⑦Inspection API에 %인코딩 URL을 보내면 색인된 글도 unknown으로 나오는 함정.
- ⑦을 고치자 **진실이 드러남: 색인 0/29가 아니라 24/29** — 신청 기준 초과. 6회차 신청을 9/3 아침 자동 대행으로 예약.
- **교훈 ⑤**: 측정이 틀리면 전략 전체가 틀린다. 대시보드 숫자는 반드시 교차 검증하라(SC UI · site: 검색 · API 삼각측량).

## 3. 버전0의 기술 스택 (아키텍처 슬라이드용)

- **비용 0원 스택**: GitHub Actions(실행) + GitHub Pages(앱 호스팅) + 무료 Gemini 키(BYOK) + Supabase 무료(동기화·큐) + 텔레그램(알림)
- 파이프라인: `main.py`(오케스트레이터) / `topics·metrics`(주제·검색량) / `generator`(생성+사람검수층) / `quality`(게이트) / `accuracy`(최신성 재작성) / `images`(Gemini 도해) / `publisher`(WP·IndexNow·WebSub) / `insights`(SC·GA) / `scripts/*`(색인검사·점검수리·핑)
- 앱: 단일 index.html PWA(v130), localStorage+AES-GCM 기기 동기화, GitHub API로 시크릿·파일 원탭 등록
- 데이터 단일 소스: `data/site_categories.json`(카테고리·mix·금지어·indexnow·auto_repair)

## 5. 버전0이 남긴 원칙 (강의 클로징)

1. 승인은 콘텐츠 문제이기 전에 **측정 문제**다 — 색인·품질·니치를 숫자로 보라.
2. 자동화 불가 항목은 감지는 전자동, 수정은 "딥링크+3클릭 카드 1장".
3. 임계값은 관념이 아니라 **실측으로 보정**한다.
4. 내가 겪은 문제는 전부 **제품 기능**이 된다 — 이 문서 자체가 그 증거.
5. 반복 작업은 반드시 자동화한다. 두 번 하면 늦은 것이다.
